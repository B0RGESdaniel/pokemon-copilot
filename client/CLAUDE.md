# CLAUDE.md (client)

This file provides guidance to Claude Code when working in `client/`. See the repo root `CLAUDE.md` for project-wide context (what this app is, cross-cutting rules shared with `server/`).

## Commands

Run from this directory (`client/`) — there is no root `package.json`.

- `npm run dev` — Vite dev server (expects the API at `http://localhost:3333/api`, override with `VITE_API_URL`)
- `npm run typecheck` — `tsc -b`
- `npm run lint` — oxlint
- `npm run build` — typecheck + Vite build

No test suite exists (no test runner installed, no test files). Verify changes with `typecheck`/`lint` and by running the app (`npm run dev`) rather than proposing a test command that doesn't exist. Don't use playwright/chromium-cli or other heavy browser automation to verify UI changes — typecheck, lint, and manual/curl-level checks are the expected bar here. The server (`server/`) must also be running (on port 3333) for the app to work end-to-end.

## Architecture

Single-page app, no router — `app/App.tsx` owns top-level view state (active save, tab, open modals) via `useState`, not URL-driven.

- **Data layer**: TanStack Query for all server state. `hooks/data.ts` and `hooks/useBattle.ts` wrap `api/*.ts` fetch functions with `useQuery`/`useMutation`; query keys are centralized in `api/queryKeys.ts` — reuse/extend that object rather than inlining key arrays. `api/client.ts` has the raw `get/post/put/patch/del` helpers (thin fetch wrapper, throws `ApiError`). The `QueryClient` in `main.tsx` is wrapped in `PersistQueryClientProvider` (`@tanstack/react-query-persist-client` + `@tanstack/query-sync-storage-persister`, `localStorage`-backed, `gcTime`/`maxAge` of one week) — this exists specifically so reopening the PWA renders last-known data instantly instead of blocking on a loading screen while the Fly.io backend cold-starts (see `server/CLAUDE.md`'s Deployment section). `useSaves()` (`hooks/data.ts`) exposes `error`/`retry` distinctly from "zero saves" — `App.tsx` must keep checking `error` before the empty-state check, otherwise a failed fetch (no cached fallback) looks identical to a genuinely new user and shows `CreateSaveForm` instead of a retry screen.
- **Save selection**: `useSaves` (`hooks/data.ts`) persists the selected save id to `localStorage` and is the source of truth for which save the rest of the app operates on; `App.tsx` gates rendering on save selection/loading/error state before mounting `MainApp`.
- **File organization — one component per file, no barrel exports**: every component (including small/private ones that used to be co-located, like a panel's sub-form or a list item) gets its own file named after it. Within each `features/<domain>/`, the inline tab-content view(s) live flat at the domain's root (`features/battle/BattleTab.tsx`; `features/pokemon/PartyView.tsx`, `PcView.tsx`, `SearchView.tsx`) — no `PageShell`, rendered directly inside the existing chrome — while every full-screen sub-flow (uses `PageShell` + a back button) goes in a `pages/` subfolder: `features/battle/pages/` (`AttackPanel.tsx`, `OpponentPanel.tsx`, `MatchupPanel.tsx`, `LevelUpPanel.tsx`) and `features/pokemon/pages/` (`AddPage.tsx`, `DetailFlow.tsx`, `MovesPage.tsx`, `ItemPage.tsx`, `EvolvePage.tsx`) follow the same split. `app/` holds root/chrome components (`App.tsx`, `Header.tsx`, `Subnav.tsx`, `BottomNav.tsx`); `components/` holds domain-agnostic UI, one file per component (`Sprite.tsx`, `SectionLabel.tsx`, `PageShell.tsx`, `Stepper.tsx`, etc.), plus a `components/ui/` subfolder (see below). **`components/` has no `index.ts` barrel** — it was removed deliberately; import each component directly from its file, not from a folder-level re-export. Don't reintroduce a barrel here or in `features/`; `hooks/`, `api/`, and `types/` are unaffected by this rule (they were never split this way) and can still export multiple things per file.
- **`components/ui/` — shadcn/neobrutalism primitives**: `Button`, `Card`, `Badge`, `Input`, `Select`, `Tabs`, `Dialog`, `AlertDialog`, `Popover`, `Toast` were installed from the [neobrutalism-components](https://neobrutalism.dev) registry (shadcn/ui built on [Base UI](https://base-ui.com), not Radix) — copied and hand-adapted, not an npm package, so treat each file as owned app code, not a vendored dependency. They're restyled to reuse this app's existing pixel-art tokens (see the `@theme` block in `index.css`: `--color-main`, `--color-border`, `--radius-base`, `--shadow-shadow`, etc. all alias to the app's own `--color-blue`/`--color-ink`/etc. — the library's own default theme was never adopted) rather than shadcn's default look, and variant names on `Button` (`primary`/`secondary`/`danger`/`outlineDanger`/`ghost`) match the app's own vocabulary, not the library's (`default`/`neutral`). Domain components (`TypeBadge`, `SearchInput`, `ConfirmDialog`, `Stepper`) wrap these primitives rather than duplicating their styling. Only files under `components/ui/` use the `@/` path alias (`@/lib/utils`, `@/components/ui/button`) — everywhere else in the app keeps relative imports; don't spread the alias outside this folder. New components use `class-variance-authority` (`cva`) for variants; pre-existing ones (`utils/effectiveness.ts`, `features/battle/pages/MatchupPanel.tsx`) still use `tailwind-variants` — both coexist by design, no need to migrate the latter. `Popover` (used by `Header`'s save-switcher) follows the `Select`/`Dialog` Portal+Positioner+Popup pattern and gets outside-click/Escape dismissal for free from Base UI — prefer it over a manual `useState` + conditional render + `document` click listener for any future anchored dropdown/menu.
  - Icons come from `pixelarticons/react` (real React components, `fill="currentColor"`, recolor with `text-*` not `bg-*`) — **never** use `dangerouslySetInnerHTML`/raw SVG imports for icons inside `Toast`: `ToastContent` runs an internal `MutationObserver` (`childList`/`characterData`/`subtree`) to auto-measure height on every content change, and `dangerouslySetInnerHTML` inside that observed subtree can feed back into itself and hang the tab (confirmed — cost a `RESULT_CODE_HUNG` renderer crash once). Plain SVG-as-component icons don't have this problem anywhere else in the app.
  - `tw-animate-css` (imported in `index.css`) provides the `animate-in`/`data-open:`/`data-closed:` enter/exit classes used by `Dialog`/`AlertDialog`/`Select`/`Popover`; `Toast` skips it in favor of a simpler opacity-only transition (see the comment in `toast.tsx` — combining `border-radius` + a hard 0-blur `box-shadow` + an animated `transform` produced a corner rendering artifact, so its enter/exit animation deliberately avoids animating `transform`). These same `animate-in`/`fade-in`/`slide-in-from-*` classes only replay on fresh DOM insertion — a persistently-mounted element (like `BattleTab`'s sprite entrance) won't retrigger them just because its data changed. `BattleTab.tsx` handles this with a `useEffect` that toggles `style.animation` + forces a reflow (`el.offsetHeight`) once the relevant identity (`activePokemon.id`/`opponent.pokeApiId`) changes *and* the field is actually visible (not covered by a full-screen panel) — a plain `key`-based remount was tried first but raced against when the underlying React Query mutation's cache update landed relative to the panel closing.
  - `AlertDialogContent`/`DialogContent` center via a `fixed inset-0 flex items-center justify-center` wrapper, not `fixed top-1/2 left-1/2` + a translate transform — the latter drifts on iPad/mobile Safari when the dynamic toolbar changes the visual viewport height after layout.
  - `index.css`'s `body`/`button` resets (default font-family, cursor, etc.) live inside `@layer base`, not as unlayered rules — this lets plain Tailwind utility classes (`font-vt`, `font-pix`, ...) override them normally on any native `<button>` (`Button`, `Select`'s `SelectTrigger`, `Tabs`' `TabsTrigger`, or a plain `<button>` like `Header`'s save-switcher) without needing the `!important` suffix. Keep any future global element reset in `index.css` inside `@layer base` for the same reason — an unlayered rule always beats a layered Tailwind utility regardless of specificity.
- **Styling**: Tailwind v4 (`@tailwindcss/vite`, no separate config file needed) + `tailwind-variants` for pre-existing component-level variant styling (see `utils/effectiveness.ts::effectivenessTier` for the pattern) alongside `cva` for `components/ui/*` (see above). Theme tokens (colors like `bg`, `ink`, `text-muted`) are Tailwind theme values, not ad hoc classes.
- **Prefer canonical Tailwind classes over arbitrary values**: an arbitrary `text-[Npx]`-style bracket value that lands exactly on an existing scale step should use the scale form instead (the editor's Tailwind extension flags these as `suggestCanonicalClasses` warnings). For spacing-scale utilities — `gap`, `p`/`px`/`py`/`m`/`mx`/`my` etc., `w`/`h`/`size`, `min-w`/`max-w`/`min-h`/`max-h`, `top`/`right`/`bottom`/`left`/`inset` — the default spacing unit is `4px`, so an arbitrary `[Npx]` converts to the decimal multiplier `N/4` (`gap-[5px]` → `gap-1.25`, `min-h-[46px]` → `min-h-11.5`, `max-w-[480px]` → `max-w-120`). Also use renamed v4 utilities where they apply (`wrap-break-word`, not the old `break-words`, for `overflow-wrap`). This does **not** apply to everything in brackets, though — three things in this app are intentionally arbitrary because they have no clean canonical equivalent: `text-[Npx]` font sizes (font-size is a named scale like `text-base`/`text-2xl`, not a linear multiplier — and this app's pixel fonts have their own deliberate grid, see below), `border-[Npx]` (border-width is a small fixed scale — 0/1/2/4/8 — not a linear multiplier, so `border-[3px]` has no canonical form), and `tracking-[Npx]` (letter-spacing's named scale is non-linear em values). Leave those as arbitrary values.
- **Fonts**: `font-pix` is Press Start 2P (the app's pixel-art display font); `font-vt` is JetBrains Mono, used for secondary/numeric text (`Lv 100`, hints, stat values) — after trying and rejecting several alternatives for that role (VT323, Geist Pixel, Silkscreen, Jersey 10, Share Tech Mono), landing on a real coding monospace font. `font-vt` is set **bold by default** (`.font-vt, input { font-weight: 700; }` in `index.css`) since JetBrains Mono only has weight 700 loaded (see `index.html`'s Google Fonts link) and it reads better bold at this app's small sizes.
- **Pixel-font sizing (`font-pix` only)**: `-webkit-font-smoothing: none` is scoped to `.font-pix` and `button` (not the whole `body`) in `index.css` — it's specifically what makes Press Start 2P's blocky glyphs render crisply; forcing it on other fonts (like `font-vt`) makes them look faint/blurry, which is why it's *not* applied globally. Press Start 2P is exactly 1em per character (true monospace); its grid is **multiples of 8px** (`text-[8px]`, `text-[16px]`, `text-[24px]`...). Never use an in-between value (`text-[7px]`, `text-[9px]`, `text-[15px]`, `text-[20px]`, etc.) — round to the nearest rung, preserving whatever hierarchy already existed (something visibly bigger than its neighbors should land on a *higher* rung, not get flattened to the same one as everything else). `font-vt` has no such grid (arbitrary values like `text-[13px]`/`text-[14px]` are normal for it) — when a piece of `font-pix` text needs to grow only modestly (the next `font-pix` rung up would nearly double its width), switch it to `font-vt` at a moderate size instead of jumping rungs.
  - Before bumping any size up a rung (or switching a `font-pix` element to a larger `font-vt` size), check the element isn't sharing a single line with other fixed-width siblings (a badge, a button, another span) — a size jump can nearly double the rendered width, and several spots in this app (the `w-28` battle action-button column, the save-switcher dropdown, the `w-15.5` stat-label column) are too narrow to survive it carelessly. When in doubt, keep the smaller size rather than guess.
- **Duplicated domain logic**: `client/src/utils/effectiveness.ts::multiplierAgainst` intentionally mirrors `server/src/modules/battle/battle.service.ts::multiplierAgainst` — it's a client-side read over a type chart the server already computed and sent down, not an independent implementation. If the effectiveness formula changes, change both.
- **PWA / mobile chrome**: `index.html`'s viewport meta includes `viewport-fit=cover` specifically so `env(safe-area-inset-*)` reports real values on iOS — without it the env vars are always `0px`. `Header`, `PageShell`'s header row, and `CreateSaveForm`'s header row pad their top with `env(safe-area-inset-top)` (stacked on top of their normal padding via `calc()`). The root layout containers use `h-dvh`, not `h-screen` (`100vh`) — `100vh` on mobile Safari/Chrome ignores the browser's dynamic address-bar height, which was cutting off the bottom nav until the toolbar collapsed.
  - **`BottomNav`'s pill styling is on each individual tab, not the bar itself** — the bar is a plain full-width, in-flow `flex-none` row (last child of `MainApp`'s flex column, like any ordinary chrome element), built on `components/ui/tabs.tsx` (`Tabs`/`TabsList`/`TabsTrigger`, same Base UI primitive `Subnav` uses); each `TabsTrigger` is individually `rounded-full` and `flex-1`. A floating/detached pill (the whole bar as a margined, centered capsule via `fixed` + `justify-center`) was tried and reverted — it overflowed and didn't center correctly. `BottomNav` has no bottom safe-area handling (`env(safe-area-inset-bottom)`) — it was deliberately removed after repeatedly failing to fix a standalone-PWA-only WebKit bug (a gap under the bar exposing the dark `body` background, worse on cold launch, also appearing on in-app tab switches) where `dvh`/`svh`/`lvh` and even a JS `visualViewport.height` reading can each be mismeasured against the real viewport by a varying amount. Several structural fixes for that bug were tried and reverted (viewport unit swaps, a JS height hook, pinning `html`/`body`/`#root` against scroll/bounce, pulling the bar into its own `fixed` layer, the floating-pill-with-margin idea) — none reliably fixed it, so the bug's on-device status is currently unresolved/deprioritized. The one mitigation still in place: this is exactly why a future fix should prefer something whose correctness doesn't depend on precisely measuring the viewport, rather than another `dvh`-precision attempt.

## Deployment

Vercel project `pokemon-copilot` (org `b0rgesdaniels-projects`), auto-deploys on push to `main` via the GitHub integration.

- Project **Root Directory must be `client`** — the repo has no root `package.json` (see Commands above), so leaving it at the Vercel default (`.`) makes every git-triggered build fail; this happened once right after connecting the GitHub repo and was fixed via `vercel project update pokemon-copilot --root-directory client`.
- `VITE_API_URL` is set as a Vercel production env var, pointing at `https://pokemon-copilot-api.fly.dev/api` (must include the `/api` suffix — see `client/src/api/client.ts`).
- Vercel's per-deployment URLs (the ones with a random hash, e.g. `pokemon-copilot-<hash>-b0rgesdaniels-projects.vercel.app`) change on every deploy and are never added to the server's `CORS_ORIGIN` — always reference/use one of the *stable* aliases (the project's default `pokemon-copilot-b0rgesdaniels-projects.vercel.app`, or the custom domain below) instead.
- Custom domain `pokemon-copilot.danielborges.me` is attached to the Vercel project (`vercel domains add`). DNS is a single `A` record (`pokemon-copilot` → `76.76.21.21`) added at the registrar for `danielborges.me` — the domain's apex/root stays on GitHub Pages untouched (no nameserver change, no existing record touched). This was a deliberate choice over true path-based routing (`danielborges.me/pokemon-copilot`), which would've required either moving nameservers to Cloudflare or migrating the existing GitHub Pages site to Vercel.
- Whenever a client domain/alias actually in use changes (new custom domain, etc.), update the server's `CORS_ORIGIN` secret — see `server/CLAUDE.md`'s Deployment section.
