# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Pokemon Copilot: a personal companion app for tracking a Pokémon save file (party, PC boxes, moves, held items) and getting matchup/moveset advice during battles. Two independent packages, no shared workspace tooling — `client` (Vite/React SPA) and `server` (Fastify API), run and versioned separately.

## Commands

Run from the respective package directory (`client/` or `server/`), not the repo root — there is no root `package.json`.

**client**
- `npm run dev` — Vite dev server (expects the API at `http://localhost:3333/api`, override with `VITE_API_URL`)
- `npm run typecheck` — `tsc -b`
- `npm run lint` — oxlint
- `npm run build` — typecheck + Vite build

**server**
- `npm run dev` — `tsx watch src/server.ts` (port from `PORT` env, see `.env`)
- `npm run typecheck` — `tsc --noEmit`
- `npm run build` / `npm start` — compile to `dist/` and run
- `npm run prisma:generate` / `npm run prisma:migrate` / `npm run prisma:studio`
- `npm run lint` exists in package.json but eslint is not installed/configured — it currently fails with `eslint: command not found`. Don't rely on it; use `typecheck` instead.

No test suite exists in either package (no test runner installed, no test files). Verify changes with `typecheck` and by running the app (`npm run dev` in both packages) rather than proposing a test command that doesn't exist.

Both dev servers must run simultaneously for the app to work end-to-end (client on Vite's default port, server on 3333).

## Architecture

### Server (`server/src`)

Fastify app, one module per resource under `src/modules/<name>/`, each with a consistent 4-file shape: `*.routes.ts` (registers endpoints, prefixed with `/api` in `app.ts`) → `*.controller.ts` (parses/validates request with Zod, calls service) → `*.service.ts` (business logic, Prisma calls) → `*.types.ts` (Zod schemas + DTOs). Follow this shape for new modules.

- **Persistence**: SQLite via Prisma (`server/prisma/schema.prisma`). No enums/JSON columns (SQLite limitation) — fields like `Pokemon.location` (`"PARTY" | "PC"`) and `BattleSession.status` (`"active" | "ended"`) are plain strings validated at the application layer, matched by the corresponding union type in `*.types.ts`. `Pokemon.moves` is a JSON-stringified array in a text column, parsed in `pokemon.service.ts::toDTO`.
- **Save-scoped data**: every domain entity hangs off a `Save` (game + generation). Almost every service function takes a `saveId` and validates it exists via `save.service.ts::getSaveOrThrow` before doing anything else.
- **PokeAPI integration** (`src/lib/pokeapi/`, `src/modules/pokeapi/`): `client.ts` fetches from the public PokeAPI with retry/backoff; `cache.ts` wraps any fetch in a permanent (no-TTL) cache backed by the `PokeApiCacheEntry` table, keyed by strings like `pokemon:{id}`, `move:{name}`, `type:{name}` — species/move/type data from PokeAPI is treated as immutable. `pokeapi.service.ts` maps raw PokeAPI shapes to app DTOs and holds the generation/version-group logic:
  - `getSpeciesByGeneration` is cumulative (fetches gen 1..N and merges) since a single `/generation/{n}` call only returns species *introduced* in that generation.
  - `getTypeChartByGeneration` reconstructs historical type effectiveness using `past_damage_relations`, since type matchups have changed across generations (e.g. Steel/Dark didn't exist before Gen 2).
  - `getVersionGroupForGame` resolves a save's `game` string (e.g. `"platinum"`) to the exact moveset-relevant version group, since a `generation` groups multiple games with slightly different learnsets.
- **Battle logic** (`battle.service.ts`, `moveset.service.ts`): `BattleSession` is one row per save (upserted, not historized — starting a new battle overwrites the previous session's opponent/state). Matchup scoring (`computeMatchup`) and move scoring (`scoreMove`, used for moveset suggestions and level-up move-learning) are heuristics, not a full damage engine — see the inline rationale comments in those files before changing the scoring formulas, since a lot of the shape is driven by what PokeAPI does/doesn't expose historically (e.g. no per-generation physical/special split before Gen 4).
- **Errors**: services throw `HttpError(statusCode, message)` (`middlewares/errorHandler.ts`); the central error handler also translates `ZodError` to 400 and passes through Fastify's own 4xx errors. Don't catch-and-format errors inside services — throw `HttpError` and let the handler serialize it.

### Client (`client/src`)

Single-page app, no router — `app/App.tsx` owns top-level view state (active save, tab, open modals) via `useState`, not URL-driven.

- **Data layer**: TanStack Query for all server state. `hooks/data.ts` and `hooks/useBattle.ts` wrap `api/*.ts` fetch functions with `useQuery`/`useMutation`; query keys are centralized in `api/queryKeys.ts` — reuse/extend that object rather than inlining key arrays. `api/client.ts` has the raw `get/post/put/patch/del` helpers (thin fetch wrapper, throws `ApiError`).
- **Save selection**: `useSaves` (`hooks/data.ts`) persists the selected save id to `localStorage` and is the source of truth for which save the rest of the app operates on; `App.tsx` gates rendering on save selection/loading state before mounting `MainApp`.
- **File organization — one component per file, no barrel exports**: every component (including small/private ones that used to be co-located, like a panel's sub-form or a list item) gets its own file named after it. Within each `features/<domain>/`, the inline tab-content view(s) live flat at the domain's root (`features/battle/BattleTab.tsx`; `features/pokemon/PartyView.tsx`, `PcView.tsx`, `SearchView.tsx`) — no `PageShell`, rendered directly inside the existing chrome — while every full-screen sub-flow (uses `PageShell` + a back button) goes in a `pages/` subfolder: `features/battle/pages/` (`AttackPanel.tsx`, `OpponentPanel.tsx`, `MatchupPanel.tsx`, `LevelUpPanel.tsx`) and `features/pokemon/pages/` (`AddPage.tsx`, `DetailFlow.tsx`, `MovesPage.tsx`, `ItemPage.tsx`, `EvolvePage.tsx`) follow the same split. `app/` holds root/chrome components (`App.tsx`, `Header.tsx`, `Subnav.tsx`, `BottomNav.tsx`); `components/` holds domain-agnostic UI, one file per component (`Sprite.tsx`, `SectionLabel.tsx`, `PageShell.tsx`, `Stepper.tsx`, etc.), plus a `components/ui/` subfolder (see below). **`components/` has no `index.ts` barrel** — it was removed deliberately; import each component directly from its file, not from a folder-level re-export. Don't reintroduce a barrel here or in `features/`; `hooks/`, `api/`, and `types/` are unaffected by this rule (they were never split this way) and can still export multiple things per file.
- **`components/ui/` — shadcn/neobrutalism primitives**: `Button`, `Card`, `Badge`, `Input`, `Select`, `Tabs`, `Dialog`, `AlertDialog`, `Toast` were installed from the [neobrutalism-components](https://neobrutalism.dev) registry (shadcn/ui built on [Base UI](https://base-ui.com), not Radix) — copied and hand-adapted, not an npm package, so treat each file as owned app code, not a vendored dependency. They're restyled to reuse this app's existing pixel-art tokens (see the `@theme` block in `index.css`: `--color-main`, `--color-border`, `--radius-base`, `--shadow-shadow`, etc. all alias to the app's own `--color-blue`/`--color-ink`/etc. — the library's own default theme was never adopted) rather than shadcn's default look, and variant names on `Button` (`primary`/`secondary`/`danger`/`outlineDanger`/`ghost`) match the app's own vocabulary, not the library's (`default`/`neutral`). Domain components (`TypeBadge`, `SearchInput`, `ConfirmDialog`, `Stepper`) wrap these primitives rather than duplicating their styling. Only files under `components/ui/` use the `@/` path alias (`@/lib/utils`, `@/components/ui/button`) — everywhere else in the app keeps relative imports; don't spread the alias outside this folder. New components use `class-variance-authority` (`cva`) for variants; pre-existing ones (`utils/effectiveness.ts`, `app/BottomNav.tsx`, `features/battle/pages/MatchupPanel.tsx`) still use `tailwind-variants` — both coexist by design, no need to migrate the latter.
  - Icons come from `pixelarticons/react` (real React components, `fill="currentColor"`, recolor with `text-*` not `bg-*`) — **never** use `dangerouslySetInnerHTML`/raw SVG imports for icons inside `Toast`: `ToastContent` runs an internal `MutationObserver` (`childList`/`characterData`/`subtree`) to auto-measure height on every content change, and `dangerouslySetInnerHTML` inside that observed subtree can feed back into itself and hang the tab (confirmed — cost a `RESULT_CODE_HUNG` renderer crash once). Plain SVG-as-component icons don't have this problem anywhere else in the app.
  - `tw-animate-css` (imported in `index.css`) provides the `animate-in`/`data-open:`/`data-closed:` enter/exit classes used by `Dialog`/`AlertDialog`/`Select`; `Toast` skips it in favor of a simpler opacity-only transition (see the comment in `toast.tsx` — combining `border-radius` + a hard 0-blur `box-shadow` + an animated `transform` produced a corner rendering artifact, so its enter/exit animation deliberately avoids animating `transform`).
  - `AlertDialogContent`/`DialogContent` center via a `fixed inset-0 flex items-center justify-center` wrapper, not `fixed top-1/2 left-1/2` + a translate transform — the latter drifts on iPad/mobile Safari when the dynamic toolbar changes the visual viewport height after layout.
  - Components that render as a native `<button>` (`Button`, `Select`'s `SelectTrigger`) needing `font-vt` text must use `font-vt!`/`antialiased!` (Tailwind's `!important` suffix) — `index.css` has an unlayered `button { font-family: font-pix }` rule that beats any Tailwind utility class on cascade-layer priority alone, regardless of specificity.
- **Styling**: Tailwind v4 (`@tailwindcss/vite`, no separate config file needed) + `tailwind-variants` for pre-existing component-level variant styling (see `utils/effectiveness.ts::effectivenessTier` for the pattern) alongside `cva` for `components/ui/*` (see above). Theme tokens (colors like `bg`, `ink`, `text-muted`) are Tailwind theme values, not ad hoc classes.
- **Prefer canonical Tailwind classes over arbitrary values**: an arbitrary `text-[Npx]`-style bracket value that lands exactly on an existing scale step should use the scale form instead (the editor's Tailwind extension flags these as `suggestCanonicalClasses` warnings). For spacing-scale utilities — `gap`, `p`/`px`/`py`/`m`/`mx`/`my` etc., `w`/`h`/`size`, `min-w`/`max-w`/`min-h`/`max-h`, `top`/`right`/`bottom`/`left`/`inset` — the default spacing unit is `4px`, so an arbitrary `[Npx]` converts to the decimal multiplier `N/4` (`gap-[5px]` → `gap-1.25`, `min-h-[46px]` → `min-h-11.5`, `max-w-[480px]` → `max-w-120`). Also use renamed v4 utilities where they apply (`wrap-break-word`, not the old `break-words`, for `overflow-wrap`). This does **not** apply to everything in brackets, though — three things in this app are intentionally arbitrary because they have no clean canonical equivalent: `text-[Npx]` font sizes (font-size is a named scale like `text-base`/`text-2xl`, not a linear multiplier — and this app's pixel fonts have their own deliberate grid, see below), `border-[Npx]` (border-width is a small fixed scale — 0/1/2/4/8 — not a linear multiplier, so `border-[3px]` has no canonical form), and `tracking-[Npx]` (letter-spacing's named scale is non-linear em values). Leave those as arbitrary values.
- **Fonts**: `font-pix` is Press Start 2P (the app's pixel-art display font); `font-vt` is JetBrains Mono, used for secondary/numeric text (`Lv 100`, hints, stat values) — after trying and rejecting several alternatives for that role (VT323, Geist Pixel, Silkscreen, Jersey 10, Share Tech Mono), landing on a real coding monospace font. `font-vt` is set **bold by default** (`.font-vt, input { font-weight: 700; }` in `index.css`) since JetBrains Mono only has weight 700 loaded (see `index.html`'s Google Fonts link) and it reads better bold at this app's small sizes.
- **Pixel-font sizing (`font-pix` only)**: `-webkit-font-smoothing: none` is scoped to `.font-pix` and `button` (not the whole `body`) in `index.css` — it's specifically what makes Press Start 2P's blocky glyphs render crisply; forcing it on other fonts (like `font-vt`) makes them look faint/blurry, which is why it's *not* applied globally. Press Start 2P is exactly 1em per character (true monospace); its grid is **multiples of 8px** (`text-[8px]`, `text-[16px]`, `text-[24px]`...). Never use an in-between value (`text-[7px]`, `text-[9px]`, `text-[15px]`, `text-[20px]`, etc.) — round to the nearest rung, preserving whatever hierarchy already existed (something visibly bigger than its neighbors should land on a *higher* rung, not get flattened to the same one as everything else).
  - Before bumping any size up a rung, check the element isn't sharing a single line with other fixed-width siblings (a badge, a button, another span) — a rung jump can nearly double the rendered width, and several spots in this app (the `w-28` battle action-button column, the 260px save-switcher dropdown, the `w-15.5` stat-label column) are too narrow to survive it. When in doubt, keep the smaller rung rather than guess.
- **Duplicated domain logic**: `client/src/utils/effectiveness.ts::multiplierAgainst` intentionally mirrors `server/src/modules/battle/battle.service.ts::multiplierAgainst` — it's a client-side read over a type chart the server already computed and sent down, not an independent implementation. If the effectiveness formula changes, change both.

### Cross-cutting

- The client has **no generated/shared types** from the server — DTOs are hand-duplicated in `client/src/types/*.ts` matching the server's `*.types.ts` shapes. When changing a server DTO shape, update the matching client type by hand. Same pattern for the `GENERATION_GAMES` table (`client/src/types/saves.ts` / `server/src/modules/save/save.games.ts`) — a hand-curated, hardcoded map of valid game/generation combinations (not fetched from PokeAPI live), used both for the client's save-creation `Select` options and the server's `createSaveSchema` cross-field validation. Keep both copies in sync; the comment in the server file explains why specific PokeAPI version-groups were excluded (JP-only variants, spin-offs, DLC-only groups, games PokeAPI has no moveset data for yet).
- Existing code comments (in Portuguese) explain non-obvious *why* — historical PokeAPI quirks, deliberate scope cuts, SQLite limitations. Read them before changing the surrounding logic; they usually record a constraint that isn't visible from the code alone. Write new comments in English going forward.

## Deployment

**Server** (`server/`) → Fly.io app `pokemon-copilot-api` (region `gru`), deployed manually via `fly deploy` from `server/` — no CI, no auto-deploy on push. `Dockerfile` is a multi-stage build on `node:22-bookworm-slim` (not alpine — `better-sqlite3`'s native binding needs glibc); `fly.toml` mounts a persistent volume (`pokemon_copilot_data`) at `/data`, sets `DATABASE_URL=file:/data/prod.db`, and configures `http_service` with `min_machines_running = 0` (scales to zero when idle — expect a several-second cold start on the first request after idle time; bump to `1` if that becomes annoying).

- **Migrations run in the app's own Docker `CMD`** (`npx prisma migrate deploy && node dist/src/server.js`), not via a `fly.toml` `release_command`. `release_command` runs on a separate ephemeral machine that does **not** mount the app's volume — migrations applied there hit a throwaway SQLite file while the real `/data` volume stays empty forever. This happened once in production (`release_command` reported success, but every real request failed with `no such table: main.Save`). Don't reintroduce `release_command` for migrations on this app.
- `prisma.config.ts` lives at the package root (not inside `prisma/`) and must be explicitly `COPY`'d into the Docker runtime stage — `COPY --from=build /app/prisma ./prisma` looks like it should cover it but doesn't. Without it, `prisma migrate deploy` silently fails to load the config and errors with a misleading `datasource.url property is required` instead of a "config not found" error.
- The Docker **build** stage needs a dummy `DATABASE_URL` (`ENV DATABASE_URL="file:./prisma/dev.db"`) purely so `prisma generate` can resolve `prisma.config.ts`'s `env("DATABASE_URL")` — `generate` never connects to a real database, so the value doesn't matter, but an *unset* var makes the config throw immediately.
- `prisma.config.ts`'s `process.loadEnvFile(".env")` must stay wrapped in try/catch — there's no `.env` file in the production container (Fly injects `DATABASE_URL`/`PORT`/`CORS_ORIGIN` directly as env vars/secrets), and an unguarded call throws on the missing file.
- `server.ts` binds `host: "0.0.0.0"` — required in a container; Fastify's default (`127.0.0.1`) isn't reachable from outside it.
- CORS is env-driven: `CORS_ORIGIN` (comma-separated list, read in `app.ts`) defaults to `http://localhost:5173` for local dev. The production value is a Fly secret and must list every client origin actually in use — update it whenever a Vercel domain changes: `fly secrets set CORS_ORIGIN="https://a,https://b" -a pokemon-copilot-api` (setting a secret triggers a rolling restart automatically, no redeploy needed).

**Client** (`client/`) → Vercel project `pokemon-copilot` (org `b0rgesdaniels-projects`), auto-deploys on push to `main` via the GitHub integration.

- Project **Root Directory must be `client`** — the repo has no root `package.json` (see Commands above), so leaving it at the Vercel default (`.`) makes every git-triggered build fail; this happened once right after connecting the GitHub repo and was fixed via `vercel project update pokemon-copilot --root-directory client`.
- `VITE_API_URL` is set as a Vercel production env var, pointing at `https://pokemon-copilot-api.fly.dev/api` (must include the `/api` suffix — see `client/src/api/client.ts`).
- Vercel's per-deployment URLs (the ones with a random hash, e.g. `pokemon-copilot-<hash>-b0rgesdaniels-projects.vercel.app`) change on every deploy and are never added to the server's `CORS_ORIGIN` — always reference/use one of the *stable* aliases (the project's default `pokemon-copilot-b0rgesdaniels-projects.vercel.app`, or the custom domain below) instead.
- Custom domain `pokemon-copilot.danielborges.me` is attached to the Vercel project (`vercel domains add`). DNS is a single `A` record (`pokemon-copilot` → `76.76.21.21`) added at the registrar for `danielborges.me` — the domain's apex/root stays on GitHub Pages untouched (no nameserver change, no existing record touched). This was a deliberate choice over true path-based routing (`danielborges.me/pokemon-copilot`), which would've required either moving nameservers to Cloudflare or migrating the existing GitHub Pages site to Vercel.
